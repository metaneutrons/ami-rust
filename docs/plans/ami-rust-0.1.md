# Initiative plan: ami-rust 0.1 with ABI1, ABI11, and safe MUI

Epic: pending tracking setup
Decision state: accepted by the maintainer on 2026-10-29; tracking links pending

## Outcome and boundaries

ami-rust 0.1 shall provide a Rust-only cross-development SDK for PC x86-64
AROS with canonical `x86_64-unknown-aros-abi1` and
`x86_64-unknown-aros-abi11` targets. The public application crates are:

- `aros`: safe, task-affine `no_std` core API and allocator;
- `aros-sys`: raw AROS ABI declarations and calls;
- `aros-mui`: safe, typed MUI/Zune application API;
- `aros-mui-sys`: complete raw public MUI/Zune ABI surface.

The measured baseline at plan acceptance is narrower. `aros-sys` contains an
initial generated Exec, DOS, Utility, and Intuition subset. `aros` has a
qualified ABI1 core. `aros-mui-sys` exposes four library calls, and `aros-mui`
only owns the library and raw-created objects. The ABI11 target and library-call
backends compile, but ABI11 has no native qualification record.

Version 0.1 includes the complete public standard MUI class surface, typed
construction, attributes, methods, inheritance, notifications, the application
event loop, menus, hooks, callbacks, custom-class support, and deterministic
cleanup. Ordinary MUI applications shall not require raw tag lists, raw vector
calls, or user-written `unsafe` code. Native interfaces whose contracts admit
arbitrary foreign pointers or unknown method layouts remain available through
an explicitly unsafe expert boundary; they are not falsely marked safe and are
not silently omitted.

The pinned API inputs are the ABI1 AROS-NX source at commit
`e0d5e367d15cc7da4ebac8f9db17868756c79569` and the Deadwood ABI11 2026.09
Development SDK from release commit
`fbc242c1046cffb5e5827a4626ee62bdd45664e9`. The plan does not authorize
changes to AROS-NX or aros-tools.

The 0.1 scope excludes `std`, native Rust/Cargo/rustup execution on AROS,
non-x86-64 targets, AmigaOS, MorphOS, crates.io, APT, Homebrew, AUR, a public
ami-rust CLI, a separate `aros-intuition` crate, and publication without an
explicit maintainer command.

## Design and decisions

MUI metadata is generated by the repository's internal Rust `xtask`. The
existing `aros-api-gen` implementation becomes an internal generator library;
there is no second public executable. Maintainers run:

```text
cargo xtask generate mui
cargo xtask check mui
```

The generator reads pinned public MUI headers, rejects unrecognised syntax, and
emits a committed canonical API model plus committed Rust sources. A small
reviewed override file records only ambiguous or inherently unsafe cases.
Every public input symbol must be classified as safe, typed unsafe, raw only,
or private. Consumers do not run the generator and do not need an AROS source
checkout.

`aros-mui-sys` owns raw constants, class names, method-message layouts, and
unsafe calls. Required Intuition and BOOPSI primitives remain in
`aros-sys::intuition`. `aros-mui` owns the generic safe class, attribute,
method, object-tree, callback, and event-loop model. Generated class modules
contain declarations, not independent handwritten implementations.

The common safe API is identical on ABI1 and ABI11. If the input inventories
contain a genuine platform-specific extension, the raw symbol remains available
behind its target condition and the difference is recorded; it must not leak
into ordinary portable MUI code without an explicit design decision.

The safe implementation may use the existing `alloc` support. It must not
introduce arbitrary fixed object, callback, or application-memory quotas.
Object ownership transfer to a MUI parent must be represented once in the
generic core so generated class wrappers cannot double-dispose children.
Retained callbacks are pinned to their owning MUI scope, remain task-affine,
and cannot unwind through the native ABI.

Development uses focused compiler and generator checks. The initiative does
not create a new test framework or run the full host/native matrix after every
slice. One maintained MUI gallery/reference application supplies broad native
integration coverage; exact-candidate qualification is reserved for M7.

## Delivery and acceptance

### M1: Qualify the x86-64 ABI11 baseline

Execution: pending tracking setup
Dependencies: pinned ABI1 and ABI11 inputs stated by this plan

- M1-A1: Pin a bootable ABI11 image, complete SDK, native toolchain, and target
  contract with content identities recorded in the repository.
- M1-A2: Build and execute the same minimal Rust application on ABI1 and ABI11,
  covering entry, allocator, DOS file I/O, library open/close, and clean exit.
- M1-A3: Build and execute a minimal MUI window lifecycle on both ABIs, proving
  the ABI1 base-last and ABI11 `r12` library-call paths with exact binaries.
- M1-A4: Preserve the existing ABI1 baseline and document any necessary
  ami-rust-only ABI11 changes; AROS-NX and aros-tools remain unchanged.

### M2: Generate the canonical MUI API model with xtask

Execution: pending tracking setup
Dependencies: pinned header inputs; M1 may proceed independently

- M2-A1: Inventory every public class, superclass relation, attribute, access
  mode, method, message structure, value, version marker, and private marker in
  the selected public MUI headers.
- M2-A2: Implement a deterministic Rust parser and expression evaluator for the
  observed header grammar, with a reviewed override format for exceptions.
- M2-A3: Commit a canonical MUI API model and provenance record that identify
  every input by commit or digest and classify every public symbol.
- M2-A4: `generate mui` reproduces committed bytes, while `check mui` detects a
  changed output and a representative unsupported construct fails explicitly.

### M3: Complete raw MUI and BOOPSI bindings

Execution: pending tracking setup
Dependencies: M1 and M2

- M3-A1: Generate the complete public raw MUI class, attribute, method, value,
  and `repr(C)` message-structure surface into `aros-mui-sys`.
- M3-A2: Add all required non-variadic muimaster, Intuition, and BOOPSI calls,
  including `DoMethodA`, `DoSuperMethodA`, and `CoerceMethodA`, without exposing
  a variadic Rust ABI.
- M3-A3: Provide reviewed ABI1 and ABI11 backends, including explicit adapters
  for call shapes that do not fit the ordinary register path.
- M3-A4: Compare generated Rust layouts and selected constant values with C for
  both pinned inputs and run one raw MUI application natively on each ABI.

### M4: Implement the safe generic MUI object model

Execution: pending tracking setup
Dependencies: M3

- M4-A1: Implement task-affine `Mui`, scope, typed object, class, attribute,
  method, and builder abstractions shared by every generated class.
- M4-A2: Represent MUI parent/child ownership transfer and partial-construction
  cleanup without leaks, use-after-free, or double disposal.
- M4-A3: Safely convert supported strings, booleans, numbers, enums, and typed
  object references while isolating foreign-pointer contracts behind explicit
  unsafe types.
- M4-A4: A small safe application constructs and disposes a typed object tree
  without raw tag lists, raw vector calls, or application `unsafe` code.

### M5: Generate all public standard MUI classes

Execution: pending tracking setup
Dependencies: M4

- M5-A1: Generate a class marker, superclass relation, builder, valid
  attributes, methods, values, and API documentation for every public standard
  class in the canonical model.
- M5-A2: Make inherited attributes and methods available to subclasses without
  per-class handwritten forwarding code.
- M5-A3: Ensure every public standard class is constructible through the safe
  API where its native contract is safe, and expose every remaining operation
  through its documented typed-unsafe or raw classification.
- M5-A4: Build a safe MUI gallery/reference application using representative
  windows, layouts, text, buttons, strings, lists, registers, and menus, with no
  class-specific handwritten bindings.

### M6: Implement notifications, hooks, event loop, and custom classes

Execution: pending tracking setup
Dependencies: M5

- M6-A1: Provide typed notifications and a safe Application event loop.
- M6-A2: Bind retained hooks and callbacks to their owning scope, prevent calls
  after scope expiration, and prevent panic from crossing the native ABI.
- M6-A3: Provide safe requesters, menus, and the regular custom-class workflow;
  arbitrary foreign dispatch messages remain in the explicit expert boundary.
- M6-A4: Exercise notifications, one retained callback or hook, the event loop,
  and a custom class in the reference application on ABI1 and ABI11.

### M7: Qualify and prepare the ami-rust 0.1 release candidate

Execution: pending tracking setup
Dependencies: M1 through M6

- M7-A1: Build the exact candidate on macOS ARM64, Linux x86-64, and Linux
  ARM64 for both canonical target specifications.
- M7-A2: Execute the exact reference application candidate under the pinned
  ABI1 and ABI11 native baselines, covering normal exit, failure cleanup, file
  I/O, widgets, notifications, callback or hook, and event-loop shutdown.
- M7-A3: Record exact source, toolchain, SDK, image, binary, and evidence
  identities and complete the applicable licence and corresponding-source
  review for shipped bytes.
- M7-A4: Verify authenticated direct and rustup installation of the candidate,
  update README and user documentation, and prepare signed GitHub Release
  assets without publishing them.
- M7-A5: Publication remains a separate maintainer decision after every prior
  criterion is accepted. Crates remain Git-delivered and unpublished on
  crates.io for 0.1.

The initiative is complete only when M1 through M7 are accepted against the
same plan revision and exact release candidate. A merged implementation, a
green host build, native qualification, prepared assets, and publication are
distinct states.

## Migration, risks and verification cost

The principal risks are an ABI11 startup or call-contract defect, differences
between the two pinned public MUI surfaces, incorrect native ownership transfer,
and callback reentrancy or lifetime errors. M1 removes the platform risk before
large safe-wrapper work. M2 records surface differences before code generation.
M4 centralises ownership, and M6 centralises retained-call behavior.

Generated files can be reverted together with their canonical model without
changing the existing qualified ABI1 core. Each implementation milestone is an
independently reviewable pull request or a short ordered series. Focused local
checks run during development; native dual-ABI checks occur at the milestones
that change their behavior, and the three-host exact-candidate matrix runs only
at M7. No calendar or runner-cost estimate is accepted until the relevant M1
and M2 measurements exist.

## Decision changes

- 2026-10-29: The maintainer required ABI11 and a complete safe regular MUI API
  for 0.1. A separate Intuition facade, other targets, package registries, and
  publication remain outside this initiative.
