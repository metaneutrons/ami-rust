title: Targets and ABIs
description: What ABI-v1 and ABI-v11 are, how they differ, and how to choose the target that matches your AROS.
---

ami-rust builds for two x86-64 AROS ABI profiles. They are two different AROS code bases with different binary conventions, so a program built for one does not run on the other. **Your source code does not change:** the Cargo target selects the ABI, and the safe `aros` and `aros-mui` crates behave identically on both.

| Property | ABI-v1 | ABI-v11 |
| --- | --- | --- |
| Cargo target | `x86_64-unknown-aros-abi1` | `x86_64-unknown-aros-abi11` |
| AROS it targets | [Upstream AROS](https://github.com/aros-development-team/AROS), qualified through the [AROS-NX](https://github.com/metaneutrons/AROS-NX) integration fork | [Deadwood's AROS](https://github.com/deadwood2/AROS) port, code-named ABIv11 |
| Pinned for 0.1.0 | AROS-NX commit `e0d5e367d15c` | Deadwood tag `ABIv11_2026.09`, commit `fbc242c1046c` |
| Where to get a system | Build or obtain an upstream AROS x86-64 image | Deadwood's [ABIv11 downloads](https://axrt.org/downloads-aros-64bit) (`pc-x86_64` and `linux-x86_64`) |
| Library base passed | As the last ordinary argument | In register `r12` |

## Which target do I choose?

Choose the target that matches the AROS system your program will run on:

- If you run an **upstream AROS** build, use `x86_64-unknown-aros-abi1`.
- If you run **Deadwood's AROS**, use `x86_64-unknown-aros-abi11`.

You can build for both from the same source tree and ship one executable per ABI. Within one build, the program and every dependency use one target. There is no Cargo feature, `cfg` option or linker flag that selects the ABI, and mixing them is not supported.

## What differs

The differences sit below the safe API.

**Library calls.** Every AROS library function is reached through a vector table relative to the library base. The two ABIs hand the base to the callee differently. ABI-v1 passes it after the ordinary arguments. ABI-v11 loads it into `r12` and passes the ordinary arguments as in the System V x86-64 convention; Deadwood's [ABI specification](https://github.com/deadwood2/AROS/blob/fbc242c1046cffb5e5827a4626ee62bdd45664e9/arch/x86_64-all/ABI_SPECIFICATION) defines this. The raw `aros-sys` and `aros-mui-sys` crates carry one generated call backend per ABI, and the safe crates are written against the common interface. You only meet this if you call a raw vector yourself.

**Native layouts.** A few native structures differ between the two system headers (for example `Library` and `MsgPort`), and one structure, `spinlock_t`, exists only on ABI-v1. The native bridge compiled by [`aros-native-build`](/build-system/) adapts to each. The ABI-v1 bridge also carries an entry gate that rejects a task stack other than 128 KiB; the ABI-v11 bridge relies on the SDK start-up and does not.

**Public MUI headers.** The pinned ABI-v1 headers declare four more MUI classes than the pinned ABI-v11 public `mui.h`: `Panel`, `PanelGroup`, `PanelTitle` and `DragHandle`, with their attributes, methods and values. They are declared only for ABI-v1 targets. Using one of them on ABI-v11 is a compile error rather than a run-time failure. The [ABI differences](/reference/abi-differences/) page lists every such item. It is generated by comparing the two builds, so it stays accurate.

## What stays the same

- The whole `aros` crate: entry, `Context`, files, streams, libraries, signals, ports, messages and callbacks.
- The whole `aros-mui` crate, with the exceptions listed on the ABI differences page.
- Resource limits, error kinds, ownership and lifetime rules.
- The build workflow: install one toolchain, add one linker configuration, choose `--target`.

## Checking the system you have

A program refuses to start, with return code 20, unless the system reports `exec.library` 51 and `dos.library` 50; on ABI-v1 it also requires a task stack of exactly 128 KiB. See [Run on AROS](/run-on-aros/). Those checks guard against an incompatible system. They do not tell you *which* ABI a system implements, so keep the ABI of your image and the target of your build paired.

## Where the ABI appears in the documentation

Application documentation (guides, examples and the [API reference](/reference/)) does not carry an ABI axis. The ABI appears in three places:

- this page and the [compatibility](/compatibility/) boundary;
- the generated [ABI differences](/reference/abi-differences/) page, and a short availability note on the few items it lists;
- the raw `*-sys` crates, where the call conventions are implemented.
